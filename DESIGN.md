# Design Register

## Visual direction

The platform console shares the management console's product shell and visual vocabulary so an AcornOps operator does not have to relearn navigation, typography, controls, or data surfaces. A quiet cream-clay sidebar gives the privileged environment a slightly warmer tone than the main workspace without competing with the AcornOps cream, brown, and orange palette. Primary and activation controls follow the management console; status colors retain their common meanings and never decorate.

## Physical scene

A platform administrator works from a support or security request in a bright office. They scan governance records, compare identity and workspace metadata, and perform one bounded action. The interface should remain legible under time pressure and make tenant-data boundaries continuously visible.

## Hierarchy

- Management-console logo, 256px tinted surface sidebar, and compact Lucide navigation.
- Workspaces use a distinct workspace-shell icon with a top bar and side panel; the Kubernetes Layers symbol remains reserved for cluster navigation. The Users workspace filter repeats the same workspace-shell icon.
- A persistent shield-labelled `Platform Admin` identity beneath the wordmark, reinforced by the favicon and browser title.
- The browser title stays concise as `Admin · AcornOps`; the fuller privileged context remains visible inside the interface.
- A route title and short description before controls, without category eyebrows.
- Overview is a brief product portfolio report designed to fit a normal desktop viewport without scrolling. It presents three complete contract-backed totals—workspaces, users, and connected environments—without a vague readiness badge, followed by a clean top-three connected-environment workspace ranking. Each ranking row uses an unadorned workspace link and shows total environments plus its Kubernetes-cluster and VM breakdown; the first row does not repeat the section divider. Product Signals has no subtitle and is limited to an explicit suspended-workspace count, identity verification, and environment concentration. Access-assignment totals, plan adoption, users-with-access rankings, and privileged-event totals remain absent. The governance boundary stays visible as a compact footer note.
- The sidebar ends with the management-console account-bar structure. The whole identity row is a button that opens a compact identity popover with System, Light, and Dark appearance preferences plus an explicit logout action. Account Settings stays absent because platform-admin profile, password, MFA, and credential lifecycle are owned by the IdP rather than this governance console.
- The confidentiality boundary remains visible in Overview's compact `Governance data only` banner, paired with a lock icon, rather than occupying a separate sidebar card or second desktop header.
- Management-console data surfaces and dense tables for discovery; quiet side panels for details.
- User details open in a right-side modal panel capped at 720px so search, filters, pagination, and scroll context remain visible behind it; compact layouts use the same panel full-screen.
- Confirmation dialogs for mutations, with actor, subject, and consequence in plain language.

## Interaction rules

- Keyboard focus is always visible and at least 2px.
- Warm clay quietly identifies platform-admin context, active navigation, and focus; color is always paired with a shield, label, or control affordance.
- Primary controls use the management console's dark neutral treatment and activation controls use Acorn orange.
- Directory toolbars follow the management console's inventory pattern: leading-icon search, high-value filters, a `Showing X of Y` loaded-result badge, and cursor-driven `Load more` pagination. Select controls use the management console's shared `Select` values directly: 44px default trigger, 16px horizontal padding, 14px medium UI type, orange interaction border/ring, fixed overlay layer 140, management menu shadow, compact-responsive option heights, and an orange-strong selected checkmark. Dropdown menus also use the management `custom-scrollbar` values: a 5px transparent track, orange 22% rounded thumb, and orange 40% hover thumb, with thin Firefox parity. By explicit platform-console refinement, chevrons remain muted grey when open and communicate state through rotation rather than color. The Users toolbar keeps its free-text workspace field, but workspace-name and ID suggestions use the same menu surface instead of a browser-native datalist. Its native browser clear glyph is replaced by a themed accessible clear control placed before the chevron. Platform clay remains wayfinding context and does not replace the shared orange control accent.
- The Workspaces toolbar uses the same inventory rhythm as Users with a leading-icon workspace-name search, a management-aligned All statuses/Active/Suspended dropdown, loaded-result badge, and cursor-driven pagination. A compact Active/Suspended column makes access posture scannable. Because the producer does not expose a lifecycle-status query, an active status filter exhausts the existing search cursor and filters the complete result set locally; the default unfiltered view remains paginated. Plan details remain in the panel. Search maps to the existing `q` producer query and does not claim ID or creator search that the producer does not provide.
- Selecting a workspace opens a deep-linkable right-side panel while retaining directory context. `Workspace Details` presents Kubernetes connections, virtual-machine connections, current plan, creator, and creation date in that order. Kubernetes and VM values use compact neutral connected/plan-limit counters derived from `/admin/v1/system/config`; red is reserved for over-limit exceptions because ordinary capacity is context, not a success state. `Change Plan` sits directly beside the current plan value so the action remains attached to the object it changes. The dialog contains only the plan selector and supplies an accurate system-generated reason without asking for a ticket or free-form reason. There is no quota-usage row, quota override action, or separate Manage Workspace section. The aggregate member count is attached to `Workspace Access`, directly above the read-only member-and-role table.
- Workspace lifecycle is a distinct access-governance section with a more prominent Active or Suspended badge that matches the directory status vocabulary. Suspension and restoration both require typing the exact workspace name in the confirmation dialog; neither asks for a free-form reason or ticket reference, and each records an accurate system-generated reason with the administrator token. Cancel bypasses field validation and always closes the confirmation. Suspension blocks ordinary workspace-member authorization and discovery while retaining memberships, targets, workload state, references, and audit history. Restoration re-enables access through those retained memberships. Neither operation starts, stops, or modifies workloads.
- Workspace access rows are grouped by descending role privilege—Owner, Admin, Member, Auditor, Viewer, then unknown roles—and alphabetized by identity within a role tier. The default workspace view remains read-only. `Manage Access` switches the existing section into a deliberate workspace-scoped editor without navigating away. A compact person-plus action beside `Done` grants an existing user access and exposes its purpose through hover/focus text; rows update roles or revoke individual access. The complete authoritative page set disables the sole Owner while allowing co-owner changes, and the producer remains authoritative during races. Atomic ownership transfer remains contract-blocked. Bulk workspace revocation is intentionally absent from this surface. The Users panel remains the complementary user-scoped editor for managing one identity across workspaces; both entry points use the same fixed membership routes and role catalog.
- User filtering is limited to verification posture until the admin user contract exposes another actionable account state; disabled-user language must not be inferred from session or authentication data.
- Selecting a user row opens a details panel with a prominent close control, Escape support, focus containment, focus restoration, and a deep-linkable `/users/:userId` URL.
- The panel header uses the selected user's name as its accessible title and shows the email beneath it; there is no generic `User details` header or duplicate summary block. Verification remains a capitalized status in the directory table.
- A compact `User Details` section presents user ID, authentication methods, and creation date without explanatory filler. Panel section and control titles use normal title capitalization rather than harder-to-scan all-uppercase headings.
- Existing workspace memberships expose a role selector populated only from `/admin/v1/system/config` `roleTemplateKeys`; it uses the shared management-aligned select treatment, while `Update Role` stays beside the selector and is disabled until the selection changes.
- `Workspace Access` includes a compact `Grant Access` action. Its dialog lists only workspaces the selected user does not already access and roles from `roleTemplateKeys`; the mutation identifies the existing user by `userId`, forces `createUserIfMissing: false`, supplies a deterministic reason, and refreshes panel and directory counts after success.
- The select-then-update interaction is the explicit opt-in for a role mutation. It applies immediately without another dialog and sends an accurate system-generated reason required by the producer contract; optional `ticketRef` is omitted.
- `Workspace Access` lists workspaces alphabetically, shows the workspace count and a compact `Grant Access` action in its section header, and avoids a duplicate role badge. Membership lifecycle metadata sits in a quiet inline footer beneath the role controls so it remains visibly attached to the access record without competing with the workspace identity.
- Membership rows omit the raw `source` value because it has no authorization effect and can be mistaken for the user's authentication method. They show `Added` and, only when the displayed date differs, `Updated`; the footer wraps naturally on compact layouts.
- Admin Audit presents the authenticated human from the immutable OIDC issuer and subject. The ledger Actor column shows one readable administrator value only—recorded display name, then email, then immutable subject—without a role subtitle; the protected details retain the full governance-safe actor and credential evidence. The BFF workload token remains separate audit evidence and never substitutes for the human actor. The ledger translates known allowlisted action codes into concise Event labels and keeps the recorded reason directly beneath. Access grants and revocations display `Modified workspace access`, while role changes retain `Updated member role`; one `Modified workspace access` filter returns all three operations through a fixed producer `actionGroup`. Workspace suspension and restoration share `Modified workspace status`. Exact action codes remain visible as secondary context. Affected identifies `workspaceId` first, followed by `subjectType` and `subjectId` when both exist; workspace-only and subject-only events remain legible without inventing missing context. Pagination mirrors the management console audit log: 50-event cursor pages append in place, an intersection sentinel preloads the next page near the scroll boundary, and a visible secondary `Load more` button remains as the accessible fallback with loading and retry feedback.
- Success toasts follow the management console pattern: centered bottom surface, success icon, dismiss action, brief entrance motion, and an Acorn orange expiry indicator. Messages state the completed outcome without duplicating audit implementation details.
- Membership suspension is an access state, not a role. The UI must not add `suspend` to the role catalog or label the existing membership `DELETE` operation as suspension. A future reversible action requires a dedicated `/admin/v1` suspend/restore contract; the current permanent removal is labelled `Revoke workspace access` and retains last-owner protection.
- Each access record exposes a compact revoke icon beside `Update Role`, never as a role option. Its hover tooltip and accessible name say `Revoke workspace access`. The individual control uses a persistent light-danger treatment and becomes solid danger on hover. Confirmation names the user and affected workspace scope without mentioning account lifecycle, sends a deterministic contract-required reason, and retains the producer's last-owner safeguard.
- In the workspace panel, owner safeguards follow the contract's cardinality rule: the last Owner cannot be demoted or revoked, while either co-owner can be changed when another Owner remains. The producer remains authoritative if membership changes concurrently. Client-orchestrated all-workspace revocation remains absent until an atomic producer contract exists.
- The user directory omits the internal user ID beneath display names; the ID remains available in `User Details`, in row identity, and to ID-based search.
- Verification remains explicit text rather than a color-only signal. `Verified` uses the shared success green, while `Unverified` uses the readable Acorn orange for its dot and label without a filled pill. Both states use the same fixed dot-and-label grid so status dots align consistently down the table column without implying account suspension or failure.
- All-workspace offboarding is deliberately absent. The existing delete contract changes one membership at a time and cannot provide an atomic impact preview, so the production console exposes only explicit per-workspace revocation until a dedicated producer endpoint exists.
- The consumer route policy excludes session access and user-account creation. Platform administrators may grant an existing user workspace access, but cannot resolve by email or set `createUserIfMissing: true`.
- Touch targets are at least 44px on compact layouts.
- Motion is brief and removed when reduced motion is requested.
- Disabled actions explain safeguards that currently prevent completion.
- Desktop uses the management console's persistent surface sidebar; compact layouts use a modal navigation drawer with a minimal navigation header.

## Accessibility

Target WCAG 2.2 AA. Use semantic landmarks, native buttons and dialogs, labelled fields, live status messages, non-color status text, and logical focus order.

## Contract Alignment

The producer source of truth is the control-plane `/admin/v1` implementation, its Zod request schemas, OpenAPI sources, and `docs/contracts/manifest.json`. The consumer mirror is `platform-admin-console/docs/contracts/manifest.json`. Runtime routes, required scopes, allowed query names, request fields, mock fixtures, response projections, and frontend field use are machine-checked together.

The console follows these producer shapes directly:

- Pagination is `{ items, nextCursor? }`; the UI does not invent `total`.
- Plans use `{ key, name }`; the existing system configuration plan catalog supplies plan quotas for read-only connected/limit badges. Mutations send `planKey` and a system-generated `reason`, while optional `ticketRef` is omitted. Plan changes that would put existing usage over the target plan are rejected by the producer.
- Workspace limits remain producer-enforced plan data. The consumer does not allowlist or render the legacy per-workspace quota-override endpoint; plan changes that would put current usage over the selected plan are rejected by the producer.
- Admin workspace DTOs add `clusterCount`, `virtualMachineCount`, `memberCount`, `lifecycleStatus`, and optional `suspendedAt`. The console sends exact `workspaceName` and a deterministic `reason` for both suspension and restoration while omitting optional `ticketRef`. The producer keeps restore `workspaceName` optional for compatibility with existing clients but validates it whenever supplied.
- User summaries use `displayName`, `emailVerified`, `authMethods`, and `workspaceMembershipCount`; the BFF projects only the producer's nested `user`, `authMethods`, and `memberships` fields for user detail and strips session information.
- Role options use the producer's `roleTemplateKeys`, and role mutations send `role` plus a system-generated `reason`; optional `ticketRef` is omitted for the direct panel interaction without adding consumer-defined role values.
- Membership-role mutations send only `role`, `reason`, and optional `ticketRef`, matching the strict producer schema.
- Member-create mutations use the producer endpoint but are narrowed to `userId`, `role`, `createUserIfMissing: false`, `reason`, and optional `ticketRef`; email-based resolution and account creation are rejected by the BFF before forwarding.
- Member deletion preserves the producer's `204 No Content` response, and BFF-owned failures use the producer error envelope `{ error: { code, message, retryable } }`.
- Admin Audit uses the runtime fields `adminTokenId`, `action`, `outcome`, `requestId`, `metadata`, and `occurredAt`. The producer OpenAPI and manifest were corrected to match this existing runtime behavior.
- Admin Audit mirrors the workspace audit-log information architecture: Time,
  Event, Actor, Object, and Details. Outcome moves into filtering and details;
  event details expose the allowlisted opaque `correlationId` alongside five
  essential fields and continue to exclude ticket references, source-IP hashes,
  user agents, and unrestricted metadata.
- The Admin Audit details action uses the workspace audit log's Eye icon. Its
  panel copies the management-console hierarchy, divided definition rows, close
  control, and bordered monospace data block while substituting Admin Audit fields.
  The summary uses the interface font consistently and the compact panel density
  mirrors the management-console reference. The data block includes every field
  available after the BFF privacy projection, and its copy action is an icon-only
  control at the top right.

## Contract Deviation Ledger

| ID | Deviation | Reason | Control and status |
| --- | --- | --- | --- |
| DEV-001 | Browser routes use `/admin-console-api/*` instead of direct `/admin/v1/*`. | The admin bearer token must never enter browser state and the browser must remain same-origin. | BFF maps every browser route to one fixed producer route; accepted permanent boundary. |
| DEV-002 | Successful responses are narrower than producer DTOs. | Some current admin DTOs contain operational or broadly scoped fields that platform administrators must not receive. | `lib/admin-contract.mjs` projects allowlisted fields and fails closed; accepted privacy requirement. |
| DEV-003 | Admin-audit pages exclude target/run/tooling action families, target identifiers, source-IP hashes, user agents, and unrestricted metadata. | `/admin/v1/admin-audit-events` is shared with operational platform administration, while this console is governance-only. | Action-family filter and metadata allowlist are tested; accepted until a dedicated governance audit contract exists. |
| DEV-004 | The console rejects `admin:*` and operational scopes even though the producer supports them. | Least privilege and confidentiality require a narrower consumer credential. | `/admin/v1/me` is verified before upstream use; accepted permanent consumer restriction. |
| DEV-005 | The prototype originally displayed credential identity rather than a human administrator. | Shared bearer attribution could not distinguish administrators. | Resolved by dedicated OIDC login, three fixed roles, Redis admin sessions, recent-auth checks, human audit fields, and a separate BFF service credential. |
| DEV-006 | Atomic ownership transfer remains absent. | The producer now provides an authoritative paginated workspace-member read and enforces the last-owner invariant, but it does not provide an atomic transfer operation. | Use the complete paginated membership set to disable the sole Owner, permit co-owner mutations, and treat producer `LAST_OWNER` responses as authoritative during races. Track only the atomic ownership-transfer contract. |
| DEV-007 | Workspace suspension and restoration were previously disabled with retention and purge. | The producer originally had no `/admin/v1` lifecycle contract. | Resolved for suspend/restore by dedicated producer routes, lifecycle fields, exact-name confirmation, authorization blocking, and audit events. Retention countdown and purge remain blocked; no fallback to tenant or database operations exists. |
| DEV-008 | No release workflow or production image was originally defined. | Deployment identity, session, secret, and network-policy design was incomplete. | Resolved by the production Docker image contract and Helm workload, admin hostname, secret inputs, ingress split, and NetworkPolicy. |
| DEV-009 | Role options are platform-wide keys rather than a workspace-scoped role catalog. | The current admin configuration contract exposes `roleTemplateKeys` but no per-workspace role availability or role-template metadata. | The panel shows only those returned keys and does not claim workspace-specific customization; track a workspace role-catalog contract before adding richer role previews or restrictions. |
| DEV-010 | Reversible workspace-membership suspension is unavailable. | The current admin contract supports role mutation and membership deletion, but no suspended membership state or restore operation. | Do not invent a `suspend` role or mislabel deletion. Add a dedicated suspend/restore contract before exposing temporary access disablement; use membership deletion only for intentional permanent removal. |
| DEV-011 | Atomic removal of a user from every workspace is unavailable. | The current contract deletes one workspace membership per request and owner replacement is workspace-specific. | The unsafe sequential browser action was removed before production. Expose no all-workspace offboarding action until a server-side impact-preview and atomic endpoint exists. |
| DEV-012 | Workspace-filtered user discovery remains assembled in the consumer; the former workspace-member N+1 detail fan-out is resolved. | `/admin/v1/users` has no `workspaceId` query, while the new workspace-member endpoint is scoped to one workspace. | Exhaust bounded user-summary pagination only when building cross-workspace filter suggestions. Load workspace panels from the authoritative paginated workspace-member route without per-user detail reads. Track a server-side user `workspaceId` filter if catalog scale requires it. |
| DEV-013 | Existing-user workspace grants use a narrower request than the producer member-create schema. | The producer also accepts email resolution and can create a missing user when `createUserIfMissing` is true, but account lifecycle is outside this console's governance boundary. | The BFF accepts only an existing `userId`, forces `createUserIfMissing: false`, rejects email and unknown fields before forwarding, and tests the negative path. |
| DEV-014 | The platform-admin consumer excludes the producer's existing workspace quota-override endpoint and related DTO fields. | The accepted product model makes workspace limits a consequence of the selected plan and avoids a second, conflicting capacity policy in the console. | The route policy, manifest, response projection, mock, UI, requirements, and tests exclude quota overrides. The producer endpoint remains temporarily available for compatibility outside this consumer and is a tracked residual contract surface. |

Any new deviation must be added to this table in the same change as the implementation. Resolved deviations remain recorded with their resolution for historical review.

# Design Register

## Visual direction

The platform console shares the management console's product shell and visual vocabulary so an AcornOps operator does not have to relearn navigation, typography, controls, or data surfaces. A quiet cream-clay sidebar gives the privileged environment a slightly warmer tone than the main workspace without competing with the AcornOps cream, brown, and orange palette. Primary and activation controls follow the management console; status colors retain their common meanings and never decorate.

## Frontend foundation

- The browser is a React and TypeScript application built with Vite and
  Tailwind CSS using the Management Console's Tailwind preset.
- Domain-neutral controls are consumed from a repository-local `@acornops/ui`
  workspace replicated from `management-console/packages/ui`. This repository
  remains independently buildable and does not depend on a sibling checkout.
- Platform-specific pages compose shared buttons, form controls, data surfaces,
  navigation, overlays, status badges, loading states, and toast primitives.
  They do not fork those primitives through imperative DOM helpers or
  page-specific control CSS.
- The shared package remains domain-neutral. Governance routes, API clients,
  authentication, platform roles, confidentiality rules, and admin-specific
  status interpretation stay in this application.
- The route shell is fluid and bounded rather than tied to a fixed canvas.
  Compact layouts use responsive gutters and a full-height navigation drawer;
  directory tables become labelled records below 768px; audit records switch
  structure from their available container width; panels, dialogs, dropdowns,
  and toasts stay inside dynamic viewport and safe-area bounds.

## Physical scene

A platform administrator works from a support or security request in a bright office. They scan governance records, compare identity and workspace metadata, and perform one bounded action. The interface should remain legible under time pressure and make tenant-data boundaries continuously visible.

## Hierarchy

- Management-console logo, 256px tinted surface sidebar, and compact Lucide navigation. Overview is the standalone first destination. `Resource Management` contains Workspaces and Users. `Platform Settings` contains Workspace, AI Providers, and Capabilities. `Governance` contains Admin Audit. The legacy `/settings` route continues to open Workspace Settings.
- Both sidebar workspace destinations use the same restrained panel-layout icon from the earlier interface. The familiar glyph keeps Resource Management and Platform Settings visually related without conflating workspaces with buildings, clusters, or infrastructure.
- A persistent shield-labelled `Platform Admin` identity beneath the wordmark, reinforced by the favicon and browser title.
- The browser title stays concise as `Admin · AcornOps`; the fuller privileged context remains visible inside the interface.
- A route title and short description before controls, without category eyebrows.
- Overview is a brief product portfolio report designed to fit a normal desktop viewport without scrolling. Platform Footprint, Most Connected Environments, and Product Signals each use one cohesive border-only surface with the section heading inside, matching the Management Console Overview's compact internal headers, row-title/caption/data type primitives, 24-pixel section rhythm, and responsive row padding without nesting cards. Platform Footprint presents three complete contract-backed totals—workspaces, users, and connected environments—without a vague readiness badge; each footprint icon is vertically centered in a restrained clay-tinted neutral tile beside its metric so the label, value, and detail read as one aligned unit. The Workspaces metric reuses the same panel-layout icon as the workspace navigation destinations. The top-three connected-environment workspace ranking and Product Signals share an aligned, equal-width desktop row and stack on narrower screens. Each ranking row uses an unadorned workspace link and shows total environments plus its Kubernetes-cluster and VM breakdown; the first row does not repeat the section divider. When all three ranking rows are present, they divide the desktop panel height evenly so their boundaries align with the three Product Signal rows. When fewer than three ranking rows are present, they stay flush to the top instead of expanding to fill the surface height. Product Signals describes the entries as portfolio conditions that may need administrator attention and remains limited to suspended access, identity verification, and environment concentration. Its value badges share a fixed 48-pixel width so counts and percentages align without content-driven resizing. Signal item headings use sentence case while preserving dynamic workspace names, and the concentration signal reads `Most connected environments are in {workspace}`. Suspended-workspace and identity-verification value markers stay neutral regardless of state rather than grading the portfolio with red or green. Access-assignment totals, plan adoption, users-with-access rankings, and privileged-event totals remain absent. The governance boundary stays visible as a compact footer note.
- The sidebar ends with the management-console account-bar structure. The whole identity row is a button that opens a compact identity popover with System, Light, and Dark appearance preferences plus an explicit logout action. Account Settings stays absent because platform-admin profile, password, MFA, and credential lifecycle are owned by the IdP rather than this governance console.
- The confidentiality boundary remains visible in Overview's compact `Governance data only` banner, paired with a lock icon, rather than occupying a separate sidebar card or second desktop header.
- Management-console data surfaces and dense tables for discovery; quiet side panels for details.
- User details open in a right-side modal panel capped at 720px so search, filters, pagination, and scroll context remain visible behind it; compact layouts use the same panel full-screen.
- Confirmation dialogs for mutations, with actor, subject, and consequence in plain language.
- MCP and skill default creation uses the Management Console's secondary icon actions and divided dialog anatomy: neutral header with close control, scrollable form body, and a separated Cancel/primary-action footer. The MCP form is deliberately distilled to name, HTTPS endpoint, and destinations, followed by one quiet note that authentication stays in each workspace's existing MCP setup. Platform-only constraints remain explicit: defaults have no enabled control, authentication controls, credentials, credential ownership, or tool review.

## Interaction rules

- Keyboard focus is always visible and at least 2px.
- Warm clay quietly identifies platform-admin context, active navigation, and focus; color is always paired with a shield, label, or control affordance.
- Primary controls use the management console's dark neutral treatment and activation controls use Acorn orange.
- Directory toolbars follow the management console's inventory pattern: leading-icon search, high-value filters, a `Showing X of Y` loaded-result badge, and cursor-driven `Load more` pagination. Select controls use the management console's shared `Select` values directly: 44px default trigger, 16px horizontal padding, 14px medium UI type, orange interaction border/ring, fixed overlay layer 140, management menu shadow, compact-responsive option heights, and an orange-strong selected checkmark. Dropdown menus also use the management `custom-scrollbar` values: a 5px transparent track, orange 22% rounded thumb, and orange 40% hover thumb, with thin Firefox parity. By explicit platform-console refinement, chevrons remain muted grey when open and communicate state through rotation rather than color. The Users toolbar keeps its free-text workspace field, but workspace-name and ID suggestions use the same menu surface instead of a browser-native datalist. Its native browser clear glyph is replaced by a themed accessible clear control placed before the chevron. Platform clay remains wayfinding context and does not replace the shared orange control accent.
- The Workspaces toolbar spans the full directory surface. Its leading-icon workspace-name search consumes the available width before the management-aligned All statuses/Active/Suspended dropdown and compact `Showing X of Y` badge; controls stack cleanly on narrow screens. The result count uses the same shared badge component, 44-pixel height, centered alignment, horizontal padding, and tabular numerals as the Users toolbar. The count compares rendered rows with the complete governance-safe workspace catalog while the rows retain cursor-driven pagination. A compact Active/Suspended column makes access posture scannable, and Active badges restore the shared green status dot. Because the producer does not expose a lifecycle-status query, an active status filter exhausts the existing search cursor and filters the complete result set locally; the default unfiltered view remains paginated. Plan details remain in the panel. Search maps to the existing `q` producer query and does not claim ID or creator search that the producer does not provide.
- Selecting a workspace opens a deep-linkable right-side panel while retaining directory context. It uses the Management Console's established 720-pixel desktop cap rather than a workspace-only wide override; compact viewports still use the full screen. The panel header and sections use the shared compact density: each of the three content sections has 12-pixel vertical wrapper padding, Workspace Access and Workspace Lifecycle override the shared section margin to zero, horizontal insets remain 16–20 pixels, panel headings remain 16 pixels, and access-table rows retain 12-pixel vertical padding. This creates a consistent 24-pixel boundary between adjacent section contents. Workspace Details, Workspace Access, and Workspace Lifecycle rely on whitespace rather than full-width section divider lines. The directory and `Workspace Details` render the creator using display name, email, and immutable user ID as fallbacks. `Workspace Details` uses a condensed, unboxed responsive metadata grid and presents Kubernetes connections, virtual-machine connections, current plan, creator, and creation date in that order. Kubernetes and VM values use compact neutral connected/plan-limit counters derived from `/admin/v1/system/config`; red is reserved for over-limit exceptions because ordinary capacity is context, not a success state. `Change Plan` sits directly beside the current plan value so the action remains attached to the object it changes. The dialog contains only the plan selector and supplies an accurate system-generated reason without asking for a ticket or free-form reason. There is no quota-usage row, quota override action, or separate Manage Workspace section. A neutral singular/plural member-count badge is attached to `Workspace Access`; the accepted description sits above a full-width responsive table whose medium-weight User, Email, and Role headings retain the internal table structure without a bottom section divider.
- Workspace lifecycle is a distinct access-governance section with a more prominent Active or Suspended badge that matches the directory status vocabulary. Active includes the shared status dot. The dormant suspend action uses the shared pale-danger treatment so it remains findable without dominating the panel; the final confirmation retains the solid destructive treatment. Suspension and restoration both require typing the exact workspace name in the confirmation dialog. Its instruction uses sentence-case UI typography with only the dynamic workspace name emphasized so mixed-case capitalization remains visible. Neither action asks for a free-form reason or ticket reference, and each records an accurate system-generated reason with the administrator token. Cancel bypasses field validation and always closes the confirmation. Suspension blocks ordinary workspace-member authorization and discovery while retaining memberships, targets, workload state, references, and audit history. Restoration re-enables access through those retained memberships. Neither operation starts, stops, or modifies workloads.
- Workspace access rows are grouped by descending role privilege—Owner, Admin, Member, Auditor, Viewer, then unknown roles—and alphabetized by identity within a role tier. The default workspace view remains read-only. `Manage Access` switches the existing section into a deliberate workspace-scoped editor without navigating away. A compact person-plus action beside `Done` grants an existing user access and exposes its purpose through hover/focus text; rows update roles or revoke individual access. The complete authoritative page set disables the sole Owner while allowing co-owner changes, and the producer remains authoritative during races. Atomic ownership transfer remains contract-blocked. Bulk workspace revocation is intentionally absent from this surface. The Users panel remains the complementary user-scoped editor for managing one identity across workspaces; both entry points use the same fixed membership routes and role catalog.
- User filtering is limited to verification posture until the admin user contract exposes another actionable account state; disabled-user language must not be inferred from session or authentication data.
- Selecting a user row opens a details panel with a prominent close control, Escape support, focus containment, focus restoration, and a deep-linkable `/users/:userId` URL.
- The panel header uses the selected user's name as its accessible title and shows the email beneath it; there is no generic `User details` header or duplicate summary block. The directory labels identity verification as `Status` and places it immediately after `Workspaces`.
- The Users directory follows the same full-width data-surface anatomy as Workspaces: no redundant internal directory heading, a flexible leading search field, the workspace filter, verification filter, and a compact `Showing X of Y` badge in that order. The workspace filter uses the same panel-layout icon as the workspace navigation destinations. The four controls form one aligned row from tablet width upward and stack at compact widths. Semantic table column headings remain because they support scanning and responsive labels.
- A compact `User Details` section presents user ID, authentication methods, and creation date in an unboxed responsive grid without explanatory filler. The section and panel header use the same 12-pixel vertical and 16–20-pixel horizontal rhythm as Workspace Details. Authored page, section, surface, table, panel, empty-state, fieldset, and dialog headings use Title Case rather than harder-to-scan all-uppercase headings. Workspace-access revoke questions and consequence headings deliberately use calmer sentence case; product acronyms retain their canonical casing, and dynamic user and workspace names are never rewritten.
- Existing workspace memberships appear in an alphabetized responsive Workspace/Role table with a count badge and accepted description. Each row exposes a role selector populated only from `/admin/v1/system/config` `roleTemplateKeys`; it uses the shared management-aligned select treatment. A compact `Update Role` and the revoke icon form a right-aligned action group beside the selector; the square revoke control uses the selector's shared 44-pixel control height in both user- and workspace-scoped drawers. Update Role remains disabled until the selection changes and applies directly without a follow-up dialog.
- `Workspace Access` includes a compact `Grant Access` action. Its dialog lists only workspaces the selected user does not already access and roles from `roleTemplateKeys`; the mutation identifies the existing user by `userId`, forces `createUserIfMissing: false`, supplies a deterministic reason, and refreshes panel and directory counts after success.
- The select-then-update interaction is the explicit opt-in for a role mutation. It applies immediately without another dialog and sends an accurate system-generated reason required by the producer contract; optional `ticketRef` is omitted.
- `Workspace Access` lists workspaces alphabetically, shows the workspace count and a compact `Grant Access` action in its section header, and avoids a duplicate role badge. Membership lifecycle metadata sits beneath the workspace identity so it remains visibly attached to the access record without competing with role controls. Individual revocation uses the same pale-danger trigger and neutral structured confirmation as workspace-scoped access management.
- Membership rows omit the raw `source` value because it has no authorization effect and can be mistaken for the user's authentication method. They always show date-only `Added`. Date-only `Updated` appears only when the membership's update instant differs from its creation instant, so a new grant does not imply a later permission change while a same-day role update remains visible. Exact timestamps remain omitted and the footer wraps naturally on compact layouts.
- Admin Audit presents the authenticated human from the immutable OIDC issuer and subject. Its route description calls the ledger a platform-level record of privileged admin actions, directs workspace audit review to the respective workspace-level audit, stays on one line at wide desktop widths, and wraps safely on compact layouts. The ledger Actor column shows one readable administrator value only—recorded display name, then email, then immutable subject—without a role subtitle; the protected details retain the full governance-safe actor and credential evidence. The BFF workload token remains separate audit evidence and never substitutes for the human actor. Actor and Object values use regular weight so Event remains the primary scanning anchor. Each ledger row leads with one natural-language Event sentence derived from the action, workspace, affected user, role, and plan; the recorded deterministic reason supplies detail when projected fields do not. A muted secondary line shows the exact raw action code and title-cased outcome without segmented title-casing; the Details panel retains the humanized event type. New records cover authentication lifecycle and privileged mutations, including requests, successes, and failures. Read-only admin requests use structured HTTP access logs instead. Legacy read/search rows remain stored as append-only evidence but are excluded from producer results and defensively removed by the BFF. One `Modified Workspace Access` filter returns grants, revocations, and role changes through a fixed producer `actionGroup`; one `Modified Workspace Status` filter returns suspension and restoration. Affected identifies the recorded workspace name first and falls back to `workspaceId`, followed by a user display name when the subject is a user; immutable user IDs remain only in projected details. Other subject types retain their recorded identifiers. Workspace-only and subject-only events remain legible without inventing missing context. The copyable raw-event surface uses a dedicated dark-neutral token in both appearance modes. Quick time presets keep a warm-clay outlined selected state paired with `aria-pressed`, while the dark primary treatment remains reserved for applying filters. Pagination mirrors the management console audit log: 50-event cursor pages append in place, an intersection sentinel preloads the next page near the scroll boundary, and a visible secondary `Load more` button remains as the accessible fallback with loading and retry feedback.
- Event sentences omit the redundant administrator label because the adjacent
  Actor column already identifies who performed the action.
- The Admin Audit workspace filter is one name-or-ID field backed by the
  producer-owned `workspaceQuery` parameter. It matches an exact workspace ID or
  a case-insensitive literal workspace-name substring. The producer retains the
  existing exact `workspaceId` parameter for compatibility; both values remain
  bounded, parameterized, and part of their cursor signature.
- Success toasts follow the management console pattern: centered bottom surface, success icon, dismiss action, brief entrance motion, and an Acorn orange expiry indicator. Messages state the completed outcome without duplicating audit implementation details.
- Membership suspension is an access state, not a role. The UI must not add `suspend` to the role catalog or label the existing membership `DELETE` operation as suspension. A future reversible action requires a dedicated `/admin/v1` suspend/restore contract; the current permanent removal is labelled `Revoke workspace access` and retains last-owner protection.
- Each managed access record exposes a contract-provided role selector, a persistent `Update Role` button, and a compact revoke icon in the Role column. A role choice is staged locally; `Update Role` is disabled until the value changes and applies the fixed role mutation directly without another dialog. The revoke action is never a role option. Its hover tooltip and accessible name say `Revoke workspace access`; it uses a persistent light-danger treatment and becomes solid danger on hover. Confirmation uses the standard dialog anatomy, sentence-case question and consequence headings, a neutral informational consequence banner, and separate user/workspace facts so it never collapses into an empty single-line body. The final submit control remains solid danger. It does not claim account lifecycle, sends a deterministic contract-required reason, and retains the producer's last-owner safeguard.
- In the workspace panel, owner safeguards follow the contract's cardinality rule: the last Owner cannot be demoted or revoked, while either co-owner can be changed when another Owner remains. The producer remains authoritative if membership changes concurrently. Stable `LAST_OWNER` failures are translated to `Workspace must keep at least one owner` so internal producer field names never leak into operator-facing copy. Client-orchestrated all-workspace revocation remains absent until an atomic producer contract exists.
- The user directory omits the internal user ID beneath display names; the ID remains available in `User Details`, in row identity, and to ID-based search.
- Verification remains explicit text rather than a color-only signal. `Verified` uses the same shared success badge, green dot, and spacing as `Active` in the Workspaces directory. `Unverified` uses readable Acorn orange for its dot and label without a filled pill, avoiding an account-suspension or lifecycle implication.
- All-workspace offboarding is deliberately absent. The existing delete contract changes one membership at a time and cannot provide an atomic impact preview, so the production console exposes only explicit per-workspace revocation until a dedicated producer endpoint exists.
- The consumer route policy excludes session access and user-account creation. Platform administrators may grant an existing user workspace access, but cannot resolve by email or set `createUserIfMissing: true`.
- Touch targets are at least 44px on compact layouts.
- Motion is brief and removed when reduced motion is requested.
- Disabled actions explain safeguards that currently prevent completion.
- Desktop uses the management console's persistent surface sidebar; compact layouts use a modal navigation drawer with a minimal navigation header.
- Platform Settings promotes its former categories into direct sidebar destinations. `Workspace` opens `/settings/workspace` with Member Discovery and User Sign-In Methods; `AI Providers` opens `/settings/ai` with write-only Default LLM Keys followed by AI Policy. The pages retain the management console's max-width settings column, independently titled sections, descriptions, and quiet bordered control surfaces without a redundant internal tab strip. User Sign-In Methods uses two management-aligned checklist choices. Password enables password login and first-time password creation; OIDC redirects workspace users to the configured identity provider. One or both methods may be enabled, but the final selected method cannot be removed. Deployment-disabled choices remain visible, disabled, and explain their blocker inline. Platform Admin authentication remains OIDC-only. Member Discovery uses clear workspace-addition language: Directory and Exact Email immediately add an existing user, while By Invites Only adds the invited person only after acceptance. Every setting shows its effective value and deployment source, with Save and Reset kept beside the setting heading; Save remains disabled until a valid value differs from the effective setting. Default LLM Keys use three separate provider cards with green configured-status badges, management-aligned 44px write-only fields, and compact provider actions. Save key and Rotate key use the same secondary outlined CheckCircle treatment and remain disabled until a non-empty key is entered; Delete key uses the filled danger Trash treatment. All use the management-console small-button dimensions. The cards stack on compact layouts. They show OpenAI, Anthropic, and Gemini configured status, permit saving or rotation, and require a second explicit click before deletion. Key values are never rendered after submission. Deployment blockers remain inline, viewers see disabled controls, and auditors do not receive the routes.
- MCP and Skill Defaults use a canonical non-empty `availableIn` destination array. The three checkbox choices are Agents, Kubernetes, and Virtual machines; selected choices pair the native checked state with the same two-pixel clay border, pale clay fill, dark clay text, and shadowless treatment as the selected Admin Audit time filter. The desktop table uses a fixed 30/35/23/12 percent column layout for definition, availability, default, and actions, respectively, so the wider `Available In` column does not resize as destination badges are added. The `Available In` heading shares one row with a single context-aware bulk action: `Select all` when no destination is selected, otherwise `Clear`. `All` is only the table summary when all three are selected. The search field consumes the remaining table-toolbar width before the destination filter and default-count badge on one desktop row; the controls stack cleanly on compact screens. The page header states that new workspaces use the defaults while existing workspaces remain unchanged; each tab description contains only its workspace-user enablement guidance. Each record has a Management Console-style Default switch and accessible overflow menu with Edit Availability and Delete actions. The availability dialog uses the concise dynamic description `Choose where {name} will appear in.` Turning Default off preserves the definition and excludes it only from future workspace snapshots; existing workspaces remain unchanged. The list filter remains one destination and matches definitions containing that destination. MCP creation mirrors the Management Console's dialog structure but asks only for name, HTTPS endpoint, and destinations. ## Accessibility

Target WCAG 2.2 AA. Use semantic landmarks, native buttons and dialogs, labelled fields, live status messages, non-color status text, and logical focus order.

## Contract Alignment

The producer source of truth is the control-plane `/admin/v1` implementation, its Zod request schemas, OpenAPI sources, and `docs/contracts/manifest.json`. The consumer mirror is `platform-admin-console/docs/contracts/manifest.json`. Runtime routes, required scopes, allowed query names, request fields, mock fixtures, response projections, and frontend field use are machine-checked together.

The console follows these producer shapes directly:

- Pagination is `{ items, nextCursor? }`; the UI does not invent `total`.
- Plans use `{ key, name }`; the existing system configuration plan catalog supplies plan quotas for read-only connected/limit badges. Mutations send `planKey` and a system-generated `reason`, while optional `ticketRef` is omitted. Plan changes that would put existing usage over the target plan are rejected by the producer.
- Workspace limits remain producer-enforced plan data. The consumer does not allowlist or render the legacy per-workspace quota-override endpoint; plan changes that would put current usage over the selected plan are rejected by the producer.
- Admin workspace DTOs add `clusterCount`, `virtualMachineCount`, `memberCount`, `lifecycleStatus`, and optional `suspendedAt`. The console sends exact `workspaceName` and a deterministic `reason` for both suspension and restoration while omitting optional `ticketRef`. The producer keeps restore `workspaceName` optional for compatibility with existing clients but validates it whenever supplied.
- User summaries use `displayName`, `emailVerified`, `authMethods`, and `workspaceMembershipCount`; the BFF projects only the producer's nested `user`, `authMethods`, and `memberships` fields for user detail and strips session information.
- Role options use the producer's `roleTemplateKeys`, and role mutations send `role` plus a system-generated `reason`; optional `ticketRef` is omitted for the direct panel interaction without adding consumer-defined role values.
- Membership-role mutations send only `role`, `reason`, and optional `ticketRef`, matching the strict producer schema.
- Member-create mutations use the producer endpoint but are narrowed to `userId`, `role`, `createUserIfMissing: false`, `reason`, and optional `ticketRef`; email-based resolution and account creation are rejected by the BFF before forwarding.
- Platform-setting reads and writes are limited to `member_discovery`, `ai_policy`, and `user_sign_in_methods`. The User Sign-In Methods value is `{ methods }`, constrained to one or both of `password` and `oidc`; deployment constraints surface allowed methods and per-method blockers. Writes include `expectedVersion` and a deterministic reason; resets omit a value. The BFF projects typed effective values and deployment constraints without forwarding arbitrary configuration.
- Member deletion preserves the producer's `204 No Content` response, and BFF-owned failures use the producer error envelope `{ error: { code, message, retryable } }`.
- Workspace-default responses and mutations use `availableIn` as a non-empty, unique, canonical-order array of `agents`, `kubernetes`, and `virtual_machines`; the scalar list filter tests membership. During rollout, the response projector can normalize the former scalar values, but browser mutations send only the array contract.
- Admin Audit uses the runtime fields `adminTokenId`, `action`, `outcome`, `requestId`, `metadata`, and `occurredAt`. The producer OpenAPI and manifest were corrected to match this existing runtime behavior.
- Admin Audit mirrors the workspace audit-log information architecture: Time,
  Event, Actor, Object, and Details. Outcome moves into filtering and details;
  event details expose the allowlisted opaque `correlationId` alongside five
  essential fields and continue to exclude ticket references, source-IP hashes,
  user agents, and unrestricted metadata.
- The Admin Audit details action uses the workspace audit log's Eye icon. Its
  panel copies the management-console hierarchy, compact single-column
  label/value definition rows, close control, and bordered monospace data block
  while substituting Admin Audit fields.
  The summary uses the interface font consistently and the compact panel density
  mirrors the management-console reference. The data block includes every field
  available after the BFF privacy projection, and its copy action is an icon-only
  control at the top right.
